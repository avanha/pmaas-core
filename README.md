# Pluggable Monitoring and Automation Server (PMAAS)

This is the core set of packages that contains the bare minimum pmaas instance.
Most functionality should be implemented in plugins that implement the PMAAS SPI
and utilize the API.

There's a vairety of plugins now, sitting in sibling repositories, i.e. Network Monitoring in https://github.com/avanha/pmaas-plugin-netmon
 
An idea for a syntax to configure eventing / automation:

```
masterBedroom.When()
    .Temperature().LTE().Fahrenheit(80)
    .And().Hours().Between(1, 7)
    .Then(turnOffCeilingFan)
```

### Why PMAAS?

I bought some Govee Bluetooth thermometers and wanted to start using them with something other than the Govee App.
I tried Home Assistant, but found it hard to enable the plugins (at the time). I was also surprised that something
outgh to be lightweight recommended it its own Linux distribution.

Additional wants:

- I should be able to run my home on a Raspberry Pi or a VM.
- I want to use a type safe / compiled language that runs on multiple platforms.
- I want it to be extensible and customizable.  If someone doesn't like my template implementation,
  they should be able to replace it.
- I like "config as code" that can be put under version control.
- Plugins should be able to evolve independently of the core.  Ideally, the core can evolve without
  breaking existing plugins.

### Why Go?

I wanted to learn Go.  It's fairly simple, type safe and fast.  It has good support for cross-platform
development. I can develop on my Mac and create binaries for Raspberry Pis.

I can check out a template assembly, add some plugins, configure it
and execute it with `go run home-assembly`.  Go downloads the dependencies automatically,
hopefully compiles and runs.

In my opinion, Go's dependency management and versioning support are great.  I think they compare well with the java
repo managers, but support source repositories directly (I think Gradle now does as well)

#### EntityManager

A registry of entities that a plugin can contribute to the system.
Each entity has an ID, a source plugin and a Type.
The idea is that other plugins can register to receive entity add/remove events.

The convention is that the EntityManger itself can store references to the entities, since
a plugin should deregister them when they are no-longer needed or on plugin stop.  However,
references should never be exposed to other plugins to avoid memory leaks.  Rather, other
plugins can use the IDs to get stubs for making calls on the entities.  Plugins can also broadcast
messages for collaboration.

## State Persistence & Schema Evolution

The plugin interacts with the core PMAAS daemon via a decoupled persistence interface. To handle breaking changes across versions without corrupting stored state, the system implements a **Version-Stamped Envelope and Upcaster Pattern**.

### Architecture & Mechanics
1. **The Envelope:** Every state blob persisted by the core server is wrapped in a generic container storing a metadata version tag alongside the raw payload:
   ```go
   type StoredState struct {
       SchemaVersion int             `json:"schema_version"`
       Payload       json.RawMessage `json:"payload"`
   }
   ```
   
2. **Upcaster Registration:** 
During plugin initialization, the plugin registers a sequential chain of migration functions
with the host daemon (e.g., fromV1, fromV2).

3. **Execution Pipeline:** 
On read, the core server inspects the schema_version, automatically executes the registered migration pipeline
sequentially, and hands the final, current-generation struct down to the plugin as an any type for local casting.

4. **Implementation Guidelines for Struct Updates:**
- When modifying state structs: Never modify old structs in place. Always define a new struct version for breaking 
schema changes.
- Implement a pure transformation function (fromV[X]) that upgrades the legacy payload step-by-step to the next schema
generation.
- Register the upcaster chain with the host server during startup so the generic server persistence layer handles
execution without needing domain-specific business logic.

#### Complete Data Flow Example
**Write Path:**
Plugin serializes its current state struct into JSON $\rightarrow$
Host wraps it in the StoredState envelope with the latest version tag $\rightarrow$
Stored to disk/DB.

**Read Path:**
Host loads envelope $\rightarrow$
Detects version (e.g., V1) $\rightarrow$
Feeds payload through registered upcasters (fromV1 $\rightarrow$ fromV2) $\rightarrow$
Deserializes into the active struct type $\rightarrow$
Hands any to plugin ready for immediate use.

#### Paths

**Linux:** /var/lib/pmaas/${assemblyName}/${pluginTypeName}.json

**Windows:** %ProgramData%\pmaas\${assemblyName}\${pluginTypeName}.json

**MacOS:** /Library/Application Support/pmaas/${assemblyName}/${pluginTypeName}.json

##### Implementation Tip

```go
func GetDefaultDataDir(assemblyName string) string {
  if runtime.GOOS == "windows" {
    return filepath.Join(os.Getenv("ProgramData"), "PMAAS", assemblyName)
  }
  // Linux / macOS system daemon default
  return filepath.Join("/var/lib/pmaas", assemblyName)
}
```

#### 2025-06-08

I updated the threading model as described in the previous entry.  The one difference from the
original plan is that all lifecycle calls, including `Init` go through the plugin's plugin runner
goroutine.  `pluginWithConfig` exposes internal methods that allow both synchronous & asynchronous
callback execution.   

#### 2024-05-09
I've been thinking about the threading model.  Currently, incoming function
calls on the plugin instance may come in on arbitrary goroutines.  To make it safe, I've been
implementing, or planning to implement channels that will invoke the logic on the plugin's
goroutine.

However, that's a lot of repetitive complexity on each plugin.  Instead, the
core could run the plugin lifecycle methods in each plugin's own dedicated goroutine and 
implement the channel mechanism to execute callbacks in the plugin's goroutine.

The lifecycle would look something like this:

- Plugin instantiation and init: main goroutine
- Start, Pump, Stop: plugin goroutine

I suppose init could be called from the plugin goroutine as well, but we want all plugins 
to complete init before start is called.  Provider (i.e., renderer) registration must
complete before `start` so plugins can use them.

Complex plugins that want more control over their concurrency could configure the core to
skip the channel transfer and just invoke the callback directly.
